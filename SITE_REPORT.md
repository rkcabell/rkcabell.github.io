# Site Overview Report

## Overall purpose and structure

This repository powers a bifurcated personal/professional portfolio with a deliberate split between the two audiences, as outlined in `README.md:5`, `README.md:7`, `README.md:11`, and the query-key mechanism described at `README.md:15` and `README.md:17`. The `pages` folder holds the top-level screens (the personal home, the professional home, the resume landing page, and the galleries for art, cat pictures, Karuta cards, and the car project; see `pages/personal.md:1`, `pages/professional.md:1`, `pages/resume.md:1`, `pages/art.md:2`, `pages/cat.md:2`, `pages/karuta.md:2`, and `pages/Car.md:1`). Each organization (home, gallery, resume) has a dedicated layout, while the `projects` subfolder stores rich, interactive demos such as the Halvorsen attractor (`projects/halvorsen.md:1`). The `wiki` directory hosts the worldbuilding home and documentation (for example, `wiki/chapters.md:1`), and the remaining directories—`assets` for static media, `scripts` for data automation, and `_data` for shared YAML payloads—round out the structure.

## Jekyll architecture

The site metadata and build rules live in `_config.yml`, where the title, description, global download toggle, and category list are declared, and `collections_dir: wiki` plus the `chapters`, `eras`, `environments`, and `habitals` collections are all configured with canonical permalinks and sorting rules (`_config.yml:1` through `_config.yml:24`). Individual page front matter carries `categories`, `moniker`, `order`, and—where applicable—`gallery` and `protected` flags so that the navigation include can route to the right section; see the personal/professional homes (`pages/personal.md:1`, `pages/professional.md:1`), project overview pages (`pages/personal_projects.md:1`, `pages/professional_projects.md:1`), and gallery metadata (`pages/art.md:2`, `pages/cat.md:2`, `pages/karuta.md:2`, `pages/Car.md:1`). Navigation labels derive from the optional `moniker` field, while `order` controls the sorting that `navigation.html` applies when it loops over every `site.pages` with the `root` category (`_includes/navigation.html:16`). Data files feed the gallery components and world map selector—`_data/art-gallery.yml:2`, `_data/cat-gallery.yml:2`, and `_data/projects.yml:1` hold the records shown by the gallery and project templates, and `_data/maps.yml:1` lists the texture names exposed by the world page. A custom filter in `_plugins/image_src_validate.rb:3` falls back from `.png` to `.jpg` when the file on disk does not exist, ensuring the gallery layout can still render a valid `<img>` source.

## Layouts and templates

The generic HTML shell is defined in `_layouts/default.html:1`, which loads the shared stylesheet, injects `navigation.html`, and wraps every page in a consistent header/footer. The personal and professional landing screens override that shell with bespoke layouts (`_layouts/personal_homepage.html:1` and `_layouts/professional.html:1`) that layer animated gradient backgrounds, grid links, and inline scripts that tailor the blurbs and video playback for each audience. The core gallery experience uses `_layouts/gallery_layout.html:14`, which pulls in Bootstrap and the TemplateMo theme, renders `page.heading` and the `site.data` list referenced by `page.gallery`, and wires up the changeable pagination and sizing controls that rely on `resize_gallery.js` and `paginator.js` (`_layouts/gallery_layout.html:34` and `_layouts/gallery_layout.html:119`). Project detail pages inherit `_layouts/project_layout.html:8`, which loads p5.js, triggers the shared `project_navigation` include (`_includes/project_navigation.html:1`), and exposes the project sidebar (`_includes/project-sidebar.html:1`). The resume pages reuse `_layouts/resume_layout.html:36` for the PDF view, while `_layouts/dynamic_resume_layout.html:17` renders the “darkroom” overlay and card overlays plus the cursor glow and lightswitch scripts that supply the theatrical experience. Wiki content builds on `_layouts/basewiki_layout.html:1` (for the glassmorphic background and sidebar) with `_layouts/wikipage_layout.html:4` adding dynamic section indicators/back buttons and `_layouts/wikihome_layout.html:4` wiring the `three.js` world model plus quick links to each lore hub.

## Styling and assets

Styling is centralized in `assets/css/style.css`, where the project pulls in Open Sans from Google (`assets/css/style.css:7`), defines looping gradient backgrounds such as `.bg`/`.bg2`/`.bg3` (`assets/css/style.css:27`), and styles the grid of tiles used by the home pages (`assets/css/style.css:1282`). The resume experience leans on `assets/css/resume.css`, which darkens the page and defines the `#resume-bkg` treatment (`assets/css/resume.css:1` and `assets/css/resume.css:95`), while the worldbuilding sections rely on `assets/css/worldstyle.css:2` for the 3D container and wiki button layout; `_layouts/basewiki_layout.html:14` also injects `assets/css/stars.css` to create the animated starfield. Fonts are hosted under `_sass/fonts.scss:1`, and the gallery layout pulls additional theme CSS (`_layouts/gallery_layout.html:15`). Audio assets (`/assets/audio/*.mp3`) are invoked by the lightswitch script at `assets/js/lightswitch.js:5` to create the analog feel on the dynamic resume, and videos under `/assets/videos/` appear in the animated tiles on both the personal and professional grid sections (`_layouts/personal_homepage.html:109` and `_layouts/professional.html:101`). The car page loads the GLTF model from `assets/models/car/` via `assets/js/carmodel.js:1`, aligning with the gallery textures and thumbnails described in `_data/art-gallery.yml:2` and `_data/cat-gallery.yml:2`.

## Navigation and linking model

Navigation revolves around the `navigation.html` include, which first aggregates every `root` page and then renders only the `professional` or `personal` subset depending on the current page’s `categories` (`_includes/navigation.html:16`). Link labels respect the `moniker` front matter, a `site.pages` sort keyed by `order` keeps them stable, and the contact modal is wired up by `assets/js/email.js:1` with a simple honeypot. Project detail pages pull `project_navigation` (`_includes/project_navigation.html:1`) and `project_sidebar` (`_includes/project-sidebar.html:1`), the latter appending the `szosxzfarvay` or `smrfhaoc` query key so that every project link keeps the visitor on the correct side. The `clairvoyance.js` script rewrites the shared “Home” and “Projects” buttons after the page loads based on that query string to preserve the professional/personal split (`assets/js/clairvoyance.js:4`). Because the README spells out that the professional entry point is `/professional.html` while the personal entry point stays at `/index.html` and the query keys are the only way to stay on either side (`README.md:5`, `README.md:7`, `README.md:11`, `README.md:15`, `README.md:17`), the template logic further enforces that the personal navigation includes the additional social links shown only on the personal homepage.

## Content types

The site surfaces a mix of static pages, interactive projects, galleries, and lore documentation. The `pages` directory provides the landing screens, resume, and gallery entry points (`pages/personal.md:1`, `pages/professional.md:1`, `pages/resume.md:1`, `pages/art.md:2`, `pages/cat.md:2`, `pages/karuta.md:2`, and `pages/Car.md:1`), while each interactive showcase sits under `projects` with the `project_layout` wrapper (see `projects/halvorsen.md:1`). Gallery metadata lives in `_data/art-gallery.yml:2`, `_data/cat-gallery.yml:2`, and `_data/projects.yml:1`, driving the loop inside `_layouts/gallery_layout.html:80`. The worldbuilding hub and its subsections are built from the `wiki` collection pages, such as `wiki/chapters.md:1`, `wiki/eras.md:1`, `wiki/habitals.md:1`, and `wiki/environments.md:1`, with a globe `/wiki/world.html` tied to `_data/maps.yml:1`. Because new wiki content is exported to `_data` and `_chapters` through the automation scripts described in `README.md:28`–`README.md:41`, these directories serve as the source of lore for the `basewiki`, `wikipage`, and `wikihome` layouts.

## JavaScript usage

JavaScript powers the concierge navigation, the gallery controls, and the immersive visuals. `assets/js/clairvoyance.js:4` reads the `?smrfhaoc`/`?szosxzfarvay` key and re-targets the shared “Home” and “Projects” buttons to keep visitors on the intended root. Galleries rely on `assets/js/resize_gallery.js:3` to toggle thumbnail sizing and on `assets/js/paginator.js:1` to build page links for the `.tm-video-item` cells rendered by `_layouts/gallery_layout.html:77`. The world and wiki pages instantiate a textured sphere through `assets/js/worldmodel.js:1`, watching the `<select>` rendered in `wiki/world.md:11`, while the car visualization pulls in `assets/js/carmodel.js:1` from `pages/Car.md:18`. The dynamic resume’s lightswitch (`assets/js/lightswitch.js:1`) and cursor glow (`assets/js/cursor-glow.js:1`) produce the overlay effects triggered by `_layouts/dynamic_resume_layout.html:19`, and the contact modal uses `assets/js/email.js:1`. Finally, the wiki sidebar’s dropdowns behave on mobile thanks to `assets/js/mobile-dropdown.js:1`, and the interactive project entries themselves load their own scripts, for example `projects/halvorsen.md:43` referencing `js/halvorsen.js`.

## Build and deployment model

Installation relies solely on Jekyll, as the `Gemfile` installs `jekyll` and the project gemspec (`Gemfile:3`). The README instructs developers to run `bundle exec jekyll serve --livereload --trace --port 4001` or `jekyll serve --livereload --incremental --port 4001` for local previews (`README.md:21`, `README.md:23`). Cache-busting is handled by appending `site.github.build_revision` to every stylesheet URL, so the shared `/assets/css/style.css` link in `_layouts/default.html:14` (and its analogues in the gallery, project, and resume layouts) always resolves to the most recent build when GitHub Pages renders the site.

## Notable custom logic or unconventional patterns

Several bespoke patterns stitch the experience together: personal and professional navigation are derived from the `categories` front matter and filtered inside `_includes/navigation.html:16`, `project_navigation.html:1`, and `_includes/project-sidebar.html:1` so that each visitor only sees the relevant subset of buttons. Gallery pages supply their own YAML feed and conditionally add a `watermarked` wrapper when `protected` is true (`pages/art.md:8` and `_layouts/gallery_layout.html:85`), while `_plugins/image_src_validate.rb:3` transparently swaps `.png` for `.jpg` assets when the file system lacks the requested variant. The worldbuilding side is dynamically textured via `assets/js/worldmodel.js:1` and the `_layouts/wikihome_layout.html:4`/`_layouts/basewiki_layout.html:1` combination, and the `scripts/populate_galleries.py:245`, `scripts/populate_wiki.py:50`, and `scripts/process_wiki.py:203` utilities exist to pull Notion exports into `_data` and the Markdown collections, making future lore updates a matter of re-running those scripts.

## Strengths, limitations, and future extension points

This architecture shines when it comes to clearly separating personal and professional views, reusing includes to share navigation, and streaming interactive content through data-driven galleries and worldbuilding collections; the automation scripts noted above already provide a pipeline to regenerate `_data` and Markdown from Notion if the lore evolves. The query-string gating that keeps visitors on the correct side (`README.md:15`, `assets/js/clairvoyance.js:4`) is effective but also means every navigation link must either inherit that key (via `project-sidebar` and `project_navigation`) or be hardcoded, which could complicate adding new pages that do not explicitly join the root categories. Because the gallery data files, wiki collections, and project scripts are already modular, those same directories and utilities offer natural extension points for additional galleries, lore sections, or interactive demos without touching the core navigation or layout logic.

## Pain Points

The professional/personal split depends on query keys appended manually `(README.md (line 15)–README.md (line 17), navigation.html (line 16))`, and clairvoyance.js rewrites links based on those keys `(clairvoyance.js (line 4))`. Any new page or navigation item must also emit the right key, or visitors accidentally land on the wrong side; this tight coupling makes maintenance error-prone and exposes the gatekeeping logic to client-side tampering.
Galleries rely on hand‑maintained YAML feeds `(art-gallery.yml, cat-gallery.yml, gallery_layout.html (line 80))` plus the populate_galleries.py script to regenerate them. The script hardcodes filesystem paths and filename conventions, so updating images requires running that bespoke Python tool, which increases operational friction compared to a build-time discovery or data-driven approach.
Navigation filtering happens by scanning every site.pages entry and sorting by order inside navigation.html `(line 16)`, without caching or a dedicated navigation data structure. As the number of pages grows, this could slow site generation and makes it hard to reason about navigation order unless every page’s front matter is kept perfectly consistent.
The resume “darkroom” UI injects multiple inline scripts and audio assets `(dynamic_resume_layout.html (line 19), lightswitch.js (line 1), cursor-glow.js (line 1), email.js (line 1))`, but the audio loading occurs client-side with hardcoded asset names and no fallback; if a file is moved or missing, the experience silently breaks. Packaging those effects as reusable components or even guarding their dependencies would make the layout more resilient.
The wiki/world integration mixes Liquid templates with runtime three.js modules `(wikihome_layout.html (line 4), basewiki_layout.html (line 1), worldmodel.js (line 1))`. Because the import maps and scripts live in the templates rather than a bundled asset, debugging texture loading or dependency updates (e.g., the CDN version of three.js) requires editing multiple files instead of a single build artifact, which complicates maintenance.
